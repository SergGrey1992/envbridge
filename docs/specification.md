# Техническое задание для Codex: Next Runtime ENV

Ты — senior TypeScript / Next.js library architect.

Необходимо с нуля разработать самостоятельную open-source npm-библиотеку:

**Название:** `@serggrey1992/next-runtime-env`

**Основная задача:** обеспечить надёжную работу runtime environment variables в Next.js, включая клиентские и серверные компоненты, Docker standalone, SSR, hydration и страницы ошибок.

Библиотека должна позволять собрать Next.js-приложение один раз и использовать одну сборку в разных окружениях без повторного `next build`.

Это отдельный npm-проект. Не добавляй библиотеку в существующий корпоративный monorepo.

## 1. Главные принципы

1. Минимальный и понятный API.
2. Один файл конфигурации — `runtime.config.ts`.
3. Автоматическая генерация типизированных файлов.
4. Отдельные клиентский и серверный API.
5. Все переменные имеют тип `string | undefined`.
6. Никаких преобразований типов, Zod, default values или обязательных проверок значений.
7. Ленивые getters, значения не вычисляются при импорте.
8. Защита серверных переменных от попадания в браузер.
9. Совместимость с Next.js App Router.
10. Без React Provider, Context и хуков.
11. Без обязательной привязки к Tailwind, UI Kit или другим библиотекам.
12. Максимально безопасная работа генератора с существующими файлами.

Не добавляй функциональность, которая не требуется для решения этой задачи.

# 2. Основной Developer Experience

Разработчик устанавливает библиотеку:

```bash
npm install @serggrey1992/next-runtime-env
```

Создаёт единственный конфигурационный файл в корне проекта:

`runtime.config.ts`

```ts
import { defineRuntimeConfig } from '@serggrey1992/next-runtime-env/config';

export default defineRuntimeConfig({
  output: './runtime-env',

  envFiles: [
    '.env',
    '.env.development',
    '.env.test',
    '.env.staging',
    '.env.production',
  ],

  public: [
    'API_URL',
    'AUTH_URL',
    'APP_NAME',
  ],

  server: [
    'JWT_SECRET',
    'DATABASE_URL',
  ],
});
```

`output` необязателен и по умолчанию равен `./runtime-env`.

`envFiles` необязателен и по умолчанию равен `['.env']`.

Имена переменных определяются исключительно массивами `public` и `server`.

Нельзя добавлять:

```ts
type: 'string'
required: true
default: '...'
validator: ...
```

Все значения читаются как строки или `undefined`.

Не требуется использовать префикс `NEXT_PUBLIC_` для публичных переменных, потому что собственный runtime-механизм явно определяет разрешённые ключи через `public`.

Если пользователь всё же указал имя `NEXT_PUBLIC_*`, оно должно работать без build-time inlining. Не использовать прямое статическое обращение `process.env.NEXT_PUBLIC_KEY` в клиентском коде.

# 3. CLI generate

Реализовать команду:

```bash
next-runtime-env generate
```

Команда выполняет две операции:

1. Генерирует типизированные файлы `client.ts` и `server.ts`.
2. Создаёт или безопасно дополняет `.env`-файлы.

Поддержать использование через npm, pnpm и npx.

Пример:

```bash
pnpm exec next-runtime-env generate
```

## 3.1. Генерируемые файлы

По умолчанию:

```text
project/
├── runtime.config.ts
├── next.config.ts
├── runtime-env/
│   ├── client.ts
│   └── server.ts
├── .env
├── .env.development
├── .env.test
├── .env.staging
└── .env.production
```

Если указано:

```ts
output: './src/shared/config/runtime-env'
```

То файлы генерируются туда:

```text
src/shared/config/runtime-env/
├── client.ts
└── server.ts
```

Путь должен разрешаться относительно корня проекта, а не текущего внутреннего каталога CLI.

Поддержать:

```bash
next-runtime-env generate --cwd ./apps/web
```

И:

```bash
next-runtime-env generate --config ./configs/runtime.config.ts
```

Определить понятные правила разрешения путей.

## 3.2. Генерация клиентского модуля

`runtime-env/client.ts`

Целевой результат:

```ts
// AUTO-GENERATED. DO NOT EDIT.

import { getPublicEnv } from '@serggrey1992/next-runtime-env/client';

export const env = {
  get API_URL(): string | undefined {
    return getPublicEnv('API_URL');
  },

  get AUTH_URL(): string | undefined {
    return getPublicEnv('AUTH_URL');
  },

  get APP_NAME(): string | undefined {
    return getPublicEnv('APP_NAME');
  },
};
```

Использование:

```tsx
'use client';

import { env } from '@/runtime-env/client';

export function Example() {
  return <div>{env.APP_NAME}</div>;
}
```

Или:

```ts
import { env } from '@/runtime-env/client';

export const variables = {
  get API() {
    return env.API_URL;
  },
};
```

TypeScript должен автоматически предлагать имена разрешённых переменных.

```ts
env.API_URL;       // OK
env.APP_NAME;      // OK
env.DATABASE_URL;  // TypeScript Error
env.UNKNOWN;       // TypeScript Error
```

Не генерировать actual runtime values.

## 3.3. Генерация серверного модуля

`runtime-env/server.ts`

```ts
// AUTO-GENERATED. DO NOT EDIT.

import 'server-only';

import { getServerEnv } from '@serggrey1992/next-runtime-env/server';

export const env = {
  get JWT_SECRET(): string | undefined {
    return getServerEnv('JWT_SECRET');
  },

  get DATABASE_URL(): string | undefined {
    return getServerEnv('DATABASE_URL');
  },
};
```

Использование:

```ts
import { env } from '@/runtime-env/server';

const secret = env.JWT_SECRET;
```

При попытке импортировать серверный модуль в Client Component Next.js должен выдавать ошибку сборки.

В серверном runtime также должна быть защита от неправильного исполнения в браузере.

Не полагайся только на TypeScript для разграничения client/server.

Не допускать попадания секретных значений в клиентские bundles или runtime bootstrap.

## 3.4. Public API на сервере

Публичные переменные должны быть доступны не только в браузере, но и в Server Components при SSR.

Использование одного и того же `runtime-env/client.ts` в серверном и клиентском окружении должно иметь документированную семантику.

Избегать ситуаций, когда сервер отображает одно значение, а клиент получает другое.

Нельзя читать `window` при серверном импорте.

# 4. Генерация .env-файлов

Это обязательная часть библиотеки.

CLI должен уметь создавать:

```text
.env
.env.local
.env.development
.env.test
.env.staging
.env.production
```

И любые другие явно разрешённые пользователем имена по шаблону `.env.<name>`.

Настройка:

```ts
envFiles: [
  '.env',
  '.env.development',
  '.env.staging',
  '.env.production',
]
```

По умолчанию создаётся только `.env`.

Все переменные из `public` и `server` должны присутствовать в каждом выбранном файле.

Например:

```dotenv
API_URL=
AUTH_URL=
APP_NAME=
JWT_SECRET=
DATABASE_URL=
```

## 4.1. Если файла нет

Создать новый файл с пустыми значениями.

## 4.2. Если файл существует

Никогда не перезаписывать файл полностью.

Пример до генерации:

```dotenv
# Application settings

API_URL=https://dev-api.example.com
JWT_SECRET=existing-secret

CUSTOM_VALUE=hello
```

После генерации:

```dotenv
# Application settings

API_URL=https://dev-api.example.com
JWT_SECRET=existing-secret

CUSTOM_VALUE=hello

AUTH_URL=
APP_NAME=
DATABASE_URL=
```

Правила:

1. Существующие значения не менять.
2. Пустые существующие значения не переписывать.
3. Не удалять неизвестные переменные.
4. Не удалять комментарии.
5. Не менять порядок существующих строк.
6. Не менять кавычки.
7. Не форматировать существующий файл.
8. Не создавать дубликаты переменных.
9. Не заменять существующие секреты.
10. Добавлять только отсутствующие ключи в конец файла.
11. Не выводить значения в CLI-логи.
12. Повторный запуск без новых переменных не должен изменять файл.

Нужно корректно обрабатывать:

```dotenv
API_URL="https://example.com"
API_URL='https://example.com'
API_URL=
export API_URL=https://example.com
```

А также пробелы, комментарии, CRLF/LF, отсутствие завершающего переноса строки и BOM.

Для определения существующих ключей использовать безопасный синтаксический анализ строк, а не наивный поиск подстроки.

При обнаружении неоднозначных или некорректных объявлений лучше выдать диагностику, чем переписать данные.

## 4.3. Защита файлов

Генератор должен:

- Отказывать в записи вне корня проекта без явного разрешения.
- Проверять symlinks и выход за разрешённую директорию.
- Не перезаписывать пользовательские `client.ts` и `server.ts`, если они не содержат узнаваемый generated marker.
- Использовать атомарную запись там, где это возможно.
- Быть идемпотентным.
- Не копировать секретные значения в generated TypeScript.
- Предупреждать о возможном попадании `.env`-файлов с секретами в Git.

Не изменять `.gitignore` автоматически без отдельного явно документированного поведения.

```bash

```

Генерация только `.env`-файлов.

```bash
next-runtime-env generate --code-only
```

Генерация только TypeScript-модулей.

```bash
next-runtime-env generate --cwd ./apps/web
```

Указание корня проекта.

```bash
next-runtime-env generate --config ./runtime.config.ts
```

Указание пользовательского конфига.

Важная особенность Next.js:

`.env.test` является стандартным именем для тестового окружения. `.env.testing` и `.env.staging` не загружаются Next.js автоматически.

Наш CLI может создавать произвольные файлы, но не должен заявлять, что Next.js автоматически их подхватывает. В README отдельно описать передачу их значений в окружение процесса через средства развёртывания или явный запуск.

# 6. Runtime-механизм

Это самая технически ответственная часть проекта.

Нужно обеспечить получение значений именно во время выполнения приложения.

Не использовать:

- `next.config.ts -> env` для передачи runtime-значений.
- Build-time подстановку значений.
- Чтение `NEXT_PUBLIC_*` напрямую из клиентского bundle.
- Обязательный React Provider.
- Кеширование секретных значений в client-side коде.

При построении решения изучи актуальные возможности Next.js, включая App Router, Route Handlers, SSR, Script, instrumentation и standalone.

## 6.1. Сервер

`getServerEnv(key)` должен получать значение из runtime-окружения сервера.

Можно использовать динамическое чтение `process.env[key]`, но нельзя допустить случайного переноса серверного кода в браузер.

Учитывай, что чтение во время исполнения серверной функции и предварительный рендеринг страницы во время `next build` — разные вещи.

Нельзя обещать runtime-значения в build-time статическом HTML.

Опиши правила применения динамического рендеринга при необходимости.

## 6.2. Клиент

Для браузера реализовать безопасную доставку только тех переменных, которые перечислены в `public`.

Рассмотреть архитектуру с:

- Независимым runtime bootstrap.
- Отдельным endpoint или runtime script.
- Безопасным клиентским хранилищем уже инициализированных значений.
- Синхронными getters после инициализации.

Исследовать варианты и выбрать самый надёжный с учётом страниц ошибок Next.js.

Предпочтительно не требовать вручную создавать Route Handler в каждом приложении, если это возможно реализовать через библиотеку и интеграцию с Next.js.

Нельзя считать `window.__ENV__` существующим до фактической инициализации.

Обязательно определить явное поведение при обращении к getter до инициализации.

Так как итоговый API имеет тип `string | undefined`, нужно различать:

- Переменная корректно инициализирована, но отсутствует в окружении.
- Клиентская конфигурация ещё не загружена.
- Произошла ошибка bootstrap.

Рекомендую для последних двух случаев использовать отдельные диагностические ошибки, а не возвращать `undefined` молча.

Не изменять согласованный публичный API без сильной причины.

# 7. Интеграция с next.config.ts

Разработчик должен иметь возможность подключить библиотеку следующим образом:

```ts
// next.config.ts

import type { NextConfig } from 'next';

import { withRuntimeEnv } from '@serggrey1992/next-runtime-env/next';

import runtimeConfig from './runtime.config';

const nextConfig: NextConfig = {
  output: 'standalone',
};

export default withRuntimeEnv(
  nextConfig,
  runtimeConfig,
);
```

Это желаемый API, который нужно подтвердить реальным прототипом.

`withRuntimeEnv` должен сохранять остальные настройки Next.js.

Если для корректной работы потребуется дополнительная Next.js-интеграция, минимизируй её и объясни причину.

Не модифицировать недокументированные внутренние файлы Next.js или webpack chunks.

Не использовать хрупкие private API Next.js.

Если надёжное подключение исключительно через `withRuntimeEnv` невозможно, предложи минимальный необходимый публичный integration point и проверь его на реальном приложении.

# 8. Страницы ошибок — критически важная задача

Одна из основных причин создания новой библиотеки — проблемы аналогичных решений с доступностью runtime-env при переходах на страницы ошибок.

Необходимо проверить:

```text
app/page.tsx
app/not-found.tsx
app/error.tsx
app/global-error.tsx
```

И следующие случаи:

1. Обычная первоначальная загрузка.
2. Прямое открытие неизвестного URL.
3. Client-side navigation на отсутствующий маршрут.
4. Вызов `notFound()`.
5. Ошибка внутри вложенного route segment.
6. Ошибка внутри root layout.
7. Переход на `global-error.tsx`.
8. Нажатие Retry или Reset.
9. Возврат на обычную страницу.
10. Повторная загрузка браузера на странице ошибки.
11. Работа в production build.
12. Работа в standalone.

Особенно важно:

`global-error.tsx` заменяет корневой layout и содержит собственные `<html>` и `<body>`, поэтому bootstrap, привязанный исключительно к RootLayout, может оказаться недоступен.

Не строй решение, предполагающее, что RootLayout всегда присутствует.

Исключить ситуацию:

```tsx
env.API_URL === undefined
```

только потому, что пользователь попал на страницу ошибки или выполнил client-side navigation.

Если значение действительно отсутствует в runtime-окружении, `undefined` является корректным.

Если значение потеряно из-за отсутствующего bootstrap — это ошибка библиотеки.

Протестировать эти ситуации отдельно.

Не заявлять абсолютную поддержку всех сценариев, пока она не подтверждена автоматическими тестами.

# 9. SSR и Hydration

Реализовать тесты для случаев:

- Серверный HTML использует публичную переменную.
- Клиент гидратирует страницу с тем же значением.
- Значение отличается между build-time и runtime.
- Конфигурация ещё не загружена.
- Страница статически сгенерирована.
- Страница динамически рендерится.
- Приложение использует streaming SSR.
- Пользователь переходит между страницами без полной перезагрузки.

Нужно определить порядок инициализации, исключающий hydration mismatch в поддерживаемых сценариях.

Ленивые getters не решают эту проблему автоматически.

Если синхронная конфигурация недоступна до первого клиентского рендера, разработать надёжный bootstrap contract, вместо скрытого асинхронного поведения синхронного API.

# 10. Один Docker image — разные окружения

Это обязательный критерий готовности.

Должен существовать один production build:

```bash
next build
```

После этого приложение запускается с разными runtime values.

Например:

DEV:

```dotenv
API_URL=https://dev-api.example.com
APP_NAME=Development
```

PROD:

```dotenv
API_URL=https://api.example.com
APP_NAME=Production
```

Без повторного `next build`.

Требования:

- Значения корректно читаются на сервере.
- Клиент получает значения текущего окружения.
- Не используется конфигурация от предыдущего окружения.
- Нет build-time инлайнинга.
- Runtime script или endpoint не кешируется неправильно.
- Секреты не попадают в клиентские файлы.
- Проверена работа Next.js standalone.

Особенно важно учитывать CDN и браузерное кеширование runtime-конфигурации.

Не связывать публичную конфигурацию с секретными cookies или пользовательскими токенами.

# 11. Безопасность

`public` — единственный разрешающий список переменных, которые могут попасть в браузер.

`server` — отдельный список переменных, доступных только на сервере.

Требования:

1. Запретить повторение одного ключа в `public` и `server`.
2. Запретить опасные или недопустимые имена переменных.
3. Клиентский bootstrap не должен перечислять весь `process.env`.
4. Серверные значения не должны появляться в HTML, JS или JSON клиентской конфигурации.
5. Серверный generated module должен импортировать `server-only`.
6. Клиентский модуль не должен импортировать серверный конфиг.
7. Ошибка сборки при импорте server entrypoint в Client Component.
8. Безопасная сериализация строк в HTML/JavaScript.
9. Защита от script injection через переменные окружения.
10. Аккуратная политика кеширования публичной конфигурации.

Проверить случаи значений, содержащих:

```text
"
'
<
>
&
</script>
Unicode
переносы строк
```

В частности, строка `</script>` не должна позволять завершить inline script и внедрить произвольный HTML.

Помни, что любые переменные из `public` доступны посетителям сайта, даже если их имена не начинаются с `NEXT_PUBLIC_`.

# 12. Генерация TypeScript

Сгенерированные файлы должны быть:

- Валидным TypeScript.
- Форматированными.
- Совместимыми со strict mode.
- Стабильными между запусками.
- Независимыми от значений окружения при генерации.
- Понятными при отладке.

Каждый generated file должен содержать служебный комментарий.

Например:

```ts
// AUTO-GENERATED BY @serggrey1992/next-runtime-env
// DO NOT EDIT MANUALLY
```

Никаких `any`.

Не генерировать ненужные дополнительные модули.

Если нужны внутренние служебные артефакты для bootstrap, они должны находиться в документированном расположении и не содержать серверных секретов.

# 14. Тесты генератора

Обязательные тесты:

- Нет `.env` — создаётся.
- Есть `.env` — добавляются отсутствующие ключи.
- Значение уже есть — сохраняется.
- Значение пустое — сохраняется.
- Есть комментарии — сохраняются.
- Есть посторонние переменные — сохраняются.
- CRLF и LF не ломаются.
- `export KEY=value`.
- Кавычки сохраняются.
- Отсутствует финальный перенос строки.
- Многократный запуск не меняет результат.
- Конфигурация содержит дубликаты.
- Неверный output path.
- Попытка перезаписать пользовательский TypeScript.
- `--env`.
- `--env-only`.
- `--code-only`.
- `--cwd`.
- `--config`.

Проверить, что при ошибке генерации пользовательские файлы не остаются в неожиданном повреждённом состоянии.

# 21. Критерии готовности

Библиотека готова к MVP, если:

1. Работает `runtime.config.ts`.
2. Работает `next-runtime-env generate`.
3. Генерируются `client.ts` и `server.ts`.
4. Настраивается output.
5. Настраивается список envFiles.
6. Существующие `.env`-значения сохраняются.
7. Отсутствующие переменные дописываются.
8. Работают lazy getters.
9. Типы строго соответствуют конфигу.
10. Клиент не может импортировать серверный API.
11. Секреты не попадают в клиентский bundle.
12. Публичные переменные доступны на сервере и в клиенте.
13. Runtime-значения не фиксируются во время build.
14. Работает один Docker image для разных окружений.
15. Работают обычные страницы.
16. Работают 404 и notFound().
17. Работают error.tsx и global-error.tsx.
18. Работают прямые и клиентские переходы.
19. Нет hydration mismatch в поддерживаемых сценариях.
20. Проходят tests, lint, typecheck и build.
21. Устанавливаемый npm tarball работает в независимом Next.js-приложении.

Если какое-либо требование невозможно выполнить средствами документированных Next.js API, не маскируй проблему. Найди минимальный корректный компромисс и явно опиши его.
